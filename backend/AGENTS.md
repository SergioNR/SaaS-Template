# Backend rules — Express.js API

Rules describe how this codebase is written today. Follow them for all new and modified code.

## Stack & runtime

- Node.js >= 26, ESM only (`"type": "module"`), plain `.js` executed via `tsx`.
- ESLint 10 flat config (`eslint.config.mjs`) extending `airbnb-base`: 2-space indent, single quotes, semicolons, trailing commas. Run `npx eslint .` from `backend/`.
- TypeScript is used only for Prisma config (`prisma.config.ts`) and the generated client; server code stays `.js`.

## Architecture — layer rules (strict)

Request flow: `server/app.js` → middlewares → routers → controllers → models/integrations.

- `server/API/v1/routes/` — route definitions only. Middleware chain per route: `authLimiter` (credential endpoints) → `checkSchema(...)` → `sanitizerResult` → controller. No business logic, no Prisma, no third-party calls in routers. One router per bounded context (domain or audience), never one per entity. When a context accumulates divergent gates or roughly 10+ routes, split it into a `routes/<domain>/` folder of sub-routers (one per resource) composed by `<domain>/index.js`, which stays the single mount in `apiRouter.js` — see `routes/admin/` (`usersRouter`, `companiesRouter`, `statsRouter`).
- `server/controllers/` — request handlers. Own status codes and response bodies. Call models and integrations. Throw unexpected errors (Express 5 forwards async throws to the global error handler).
- `server/models/` — ALL database access lives here (repository pattern), one file per resource. Naming: `<verb><Resource>InDb` (e.g. `getUserByEmail`, `deleteUserInDb`). Controllers never import `prisma` directly.
- `server/integrations/` — third-party API calls only (`stripe/`, `brevo/`, `telegram/`), one folder per vendor. Never touch the database.
- `server/middlewares/` — one middleware per file, named export matching the file name. Factories return the handler: `checkAuthentication()`, `checkPermissionByRole(role)`.
- `server/utils/` — cross-cutting helpers (`userDeletionCleanup.js`) and `utils/validators/` with one express-validator schema file per request shape.
- `server/config/` — shared singletons and constants (`prismaClient.js`, `stripe.js`, `logger.js`, `planPrices.js`, `security.js`). No request handling.
- `server/cron/` — `CronJob` instances, started from `cron/jobsContainer.js` (registered in `app.js` via `startCronJobs()`). Errors inside the tick are caught and `logError`-ed, never thrown. Every tick runs through `runExclusiveCronTick` (`cron/exclusiveCronTick.js`): a transaction-scoped `pg_try_advisory_xact_lock` (`models/advisoryLockModel.js`, one key per job in `config/advisoryLockKeys.js`) so only one replica runs a job; the others skip the tick.
- `server/webhooks/` — inbound webhooks; raw-body only (see Security).
- `server/auth/` — Passport setup; strategies in `auth/strategies/`.

## API conventions

- All API routes are versioned under `/api/v1` and mounted in `server/API/apiRouter.js`. Health check lives in `server/routers/indexRouter.js`.
- **Role enforcement happens at the router mounting level** in `apiRouter.js` (`checkAuthentication()` + `checkPermissionByRole(role)`), not per-route. A router that mixes public and gated routes composes sub-routers explicitly — `authRouter` mounts `authPublicRouter`, then `authRouter.use(checkAuthentication(), authPrivateRouter)` — never a bare mid-file `router.use(gate)`, where file position silently decides what requires auth.
- Account self-service lives under `/api/v1/user` (`PATCH /user/password` → `userController.updateUserPassword`). `PATCH /auth/update-user-password` is a deprecated alias of the same handler kept for older clients - do not add routes to it, remove it once no client calls it.
- **Every route requires an `@openapi` JSDoc block directly above its definition.** swagger-jsdoc scans `server/routers/indexRouter.js`, `server/routers/docsRouter.js`, `server/API/v1/routes/**/*.js` (domain folders included), `server/webhooks/webhooksRouter.js`. Reuse shared response schemas via `$ref: '#/components/schemas/...'` (defined in `server/config/swagger.js`); add new shared schemas there.
- Response body is the payload itself — the HTTP status alone carries success/failure (no `success` flag). `message` is optional, English, developer-facing (API consumers/logs), present only when it adds info beyond status + payload (conflict reasons, token expiry, rate-limit, route-404, 500). `code` is optional, stable, machine-readable, only where one status covers multiple SPA-distinguishable cases (see `updateUserPassword`). Never rely on `message` wording.
- Every top-level router and domain-folder `index.js` ends with the `/*fallback` 404 handler (copy the exact shape from `userRouter.js`); nested sub-routers rely on the folder index's fallback. The root `indexRouter` uses `.all` so non-GET misses also get the JSON 404.
- Status codes: 200 success · 201 created · 400 bad/expired input · 401 unauthenticated · 403 wrong role · 404 not found · 409 conflict (duplicate, self-delete, FK constraint) · 422 validation (`sanitizerResult`) · 429 rate limited · 500 internal only via thrown errors.
- Map Prisma error codes where users interact: `P2002` (unique) → duplicate-safe response; `P2003` (FK) → 409. See `registerUser` and `deleteOneUserById` for the pattern.
- Pagination is cursor-based (`limit` capped at 100 + `cursor` + `nextCursor` in the response), `created_at desc` ordering. See `getAllUsers`.

## Security rules (non-negotiable — outcomes of past audits)

- **Enumeration-safe auth**: `register`, `password-reset` and the team invite create/resend endpoints return an identical response shape and status whether or not the invited/registered account exists, and respond before doing account-dependent work (lookup/create/email run detached; for team invites only the lookup and email - see below) so timing doesn't leak either. Never leak account existence - not even to authenticated callers. Team invites: the invite row is always written (create) or rotated (resend) synchronously, identically for registered and unregistered addresses, so `GET /team`, a repeated invite (409), resend and revoke behave the same either way and the row is never deleted because the address is registered; only the detached email differs (unregistered → invite email, registered → nothing - never the registration-worded existing-account notice). Accept rejects registered emails with 409 and keeps the invite row (also on the concurrent-registration P2002 path) - deleting it would make the invite vanish from `GET /team` and reveal the registration to the inviting company; it expires and is cleaned up like any other. Only invites with `token_expires > now` are pending: `GET /team` and the duplicate-invite 409 ignore expired rows, and creating an invite for an address that only has an expired row replaces it in the same transaction (`createTeamInviteInDb`).
- **Timing-equalized login**: nonexistent users are compared against `DUMMY_PASSWORD_HASH` (`auth/strategies/passportLocalStrategy.js`). Keep it.
- **CSRF / request shape**: state-changing requests must carry an allowlisted `Origin` (fallback `Referer`) — `middlewares/originChecker.js`, allowlist shared with CORS in `config/allowedOrigins.js` (localhost origins only when `DEPLOY_ENVIRONMENT=localhost`). `/api` bodies must be `application/json` (`jsonContentTypeChecker.js`, 415). Never re-add `express.urlencoded`. `/webhooks` and docs mount before these checks and the global limiter. The docs router (Swagger UI + `/api/docs.json`) is mounted only when `DEPLOY_ENVIRONMENT=localhost`, and its 404 fallback is scoped to `/docs/*fallback` so it never swallows `/api` requests.
- **Secret tokens** (invite, password reset): `crypto.randomBytes(32)` base64url via `utils/secureToken.js`; store only the SHA-256 in `token_hash`, send the raw token only by email, never return it in an API response. Row `id` is a public handle. Consume tokens inside a `$transaction` (conditional `deleteMany`, require `count === 1`).
- **Atomic invariants**: checks that guard a write (last company owner, caller outranks every role the target holds) run in the same `$transaction` as the write, with the company row locked (`SELECT ... FOR UPDATE`) and the caller's and the target's membership + role rows re-read under that lock (a target removed concurrently resolves to `not_found`, never a P2025 500) (`callerId` option of `deleteUserWithCompanyDataInDb` / `updateCompanyMemberRoleInDb`) - never pass pre-computed role lists into the transaction. Granting a role (invite, assign) is "at or below own rank" (`canGrantRole`); managing an existing member (remove, change role) is strict - the caller must outrank every role the target holds (`outranksAllRoles`), so peers never touch each other. Removing or demoting a member voids the invites they issued to roles they can no longer grant. An invite is only as good as its inviter (`canCompanyMemberGrantRoleInDb`, shared by the team and auth controllers): invite check/accept answer 400 `INVITER_INVALID` (expired: 400 `INVITE_EXPIRED`) and resend answers 409 `INVITER_INVALID` once the original inviter left or can no longer grant the role. The accept re-check is repeated inside `createUserInDB`'s transaction after `lockCompanyForUpdateInDb` (the outside check is only a fast path), so a concurrent removal or demotion cannot slip through; that path voids the invite in the same commit. Deletion cleanup does all DB steps in one transaction and calls Stripe/S3 only after commit.
- **Fire-and-forget side effects**: emails (Brevo), PostHog events, and `last_login_at` updates must not change the response's shape or timing — the integration/model function swallows its own errors and is called without `await`.
- **Stripe webhook**: raw body (`express.raw`) — never mount `express.json()` in front of `/webhooks`. DB writes inside the handler are `await`-ed so failures return 500 and Stripe retries.
- **Redaction**: sensitive fields are redacted in two places — `sanitizerResult.js` (`sensitiveFields`) and `logger.js` pino `redact.paths`. Update both when adding a sensitive field. Never log passwords or reset tokens.
- **Never expose internal Stripe ids**: client-facing subscription reads go through `getSubscriptionPublicDataInDb`.
- **Checkout reuse, not shared idempotency keys**: `POST /billing/checkout-session` first asks Stripe whether the customer holds a subscription in an access-granting status (`ACCESS_GRANTING_STATUSES` in `config/stripeSubscriptionStatuses.js`, shared with the webhook sync - 409 `SUBSCRIPTION_ACTIVE`). Then an open session whose metadata matches `planName` + `planBillingCycle` + `priceId` is reused (its URL returned) and every other open session is expired, so at most one checkout can complete. A new session uses a per-request `crypto.randomUUID()` idempotency key that only covers network retries of that call - never a key derived from company/plan/time (a replayed key returns a session that may have been expired). Stripe idempotency / 409 "request in progress" errors map to 409 `CHECKOUT_IN_PROGRESS`, not 500. The Stripe client runs with `timeout: 8000` and `maxNetworkRetries: 1` so requests and webhook deliveries fail fast.
- **Subscription rows**: the row `id` is always an internal uuid; the Stripe subscription lives in `stripe_subscription_id` (null = trial) with `stripe_status` and `stripe_synced_at`. "Active paid subscription" is decided only by `isStoredSubscriptionActive` (`config/stripeSubscriptionStatuses.js`) - never infer it from an id prefix.
- **Webhook sync**: read Stripe BEFORE `syncSubscriptionWithCompanyLockInDb` takes the company lock - no Stripe/network call ever runs under it. The resolver passed to the model is pure and decides against the locked row; the model drops writes whose `syncedAt` is older than the stored `stripe_synced_at` of the same subscription. The company comes from the subscription's customer (`getCompanyIdByStripeCustomerIdInDb`), never from `client_reference_id` (only cross-checked, mismatch → `logError`, skipped).
- **Company deletion billing cleanup**: `deleteUserWithCompanyDataInDb` returns `companyId` + `stripeCustomerId`; after commit `cancelCompanyBillingInStripe` expires every open Checkout Session of the customer, then cancels every access-granting subscription at period end. It never throws; every failed step is `logError`-ed with the ids to retry by hand.
- **Passwords**: native `bcrypt` (hashing runs on the libuv threadpool, not the event loop; reads the `$2a$` hashes bcryptjs wrote) with `BCRYPT_SALT_ROUNDS` (12) from `config/security.js`. Passwords that are set are capped at 72 UTF-8 bytes (`utils/validators/passwordByteLength.js`) because bcrypt ignores the rest. Queries returning users must `omit: { password: true }` - only `getUserPassword` (password change) and `getUserForLogin` (used exclusively by the passport local strategy, which strips the hash before `done`) select it. `getUserByEmail` omits it like every other lookup.
- **Query whitelist**: never pass `req.query`/`req.body` through to Prisma — whitelist explicit fields (see `getAllUsers` role filter).
- **Admin self-protection**: superadmins cannot delete their own account via `/api/v1/admin` (409) — route them to the user endpoint. The last superadmin can be deleted by neither endpoint (409 `LAST_SUPERADMIN`), checked in `deleteUserWithCompanyDataInDb` under a transaction-scoped advisory lock. Admin deletions `logInfo` the acting superadmin.
- **Required env vars fail fast at startup** via `requireEnv(name, reason)` from `config/requiredEnv.js` — throws outside localhost, only warns on `DEPLOY_ENVIRONMENT=localhost` so local dev boots with any key unset. `TRUST_PROXY` and `FRONT_WEB_APP_ORIGIN_URL` are required outside localhost; never hard-code `trust proxy`.
- **No localhost mode in production**: `config/environmentGuard.js` (first import of `app.js`) throws at boot when `NODE_ENV=production` and `DEPLOY_ENVIRONMENT=localhost` - that mode disables the session secret, limiters, secure cookies and error hiding.
- New env vars must be added to `.env.example` and the README table in the same change.

## Validation

- One express-validator schema per request shape in `server/utils/validators/`, mounted as `checkSchema(...)` followed by `sanitizerResult` (rejects with 422 before any controller runs).
- Login, register, invite check/accept (`GET /auth/invite`, `POST /auth/invite-accept`) and the password-reset check/submit (GET/PATCH) routes share the `authLimiter` budget (10 req / 15 min per IP). Login additionally has `loginAccountLimiter` (5 failed attempts / 15 min per normalized username **+ client IP** - the IP in the key keeps an attacker from locking a victim out of their own account by exhausting the budget from elsewhere). The password-reset request route gets its own `passwordResetLimiter` (5 req / 1 hour per IP) so reset emails are throttled independently of login failures. Global limiter (100 req / 15 min) + capped slow-down apply everywhere except local dev, `/webhooks` and docs. `/webhooks` has its own always-on `webhookLimiter` (300 req / 1 min per IP, `webhooks/webhookRateLimiter.js`, also active in local dev) - far above Stripe's delivery rate, but a ceiling on what can be pushed through signature verification. Custom `keyGenerator`s that include the client IP must pass it through `ipKeyGenerator(req.ip)` from `express-rate-limit` (IPv6 addresses are collapsed to their /56 subnet), never raw `req.ip`. Limiters are in-memory per process.
- Don't `escape` emails, passwords or filenames in validators — it corrupts stored data (`o'brien@x.com`); escape on output instead.

## Sessions & auth

- **Two independent role layers — never mix them.**
  - Platform role `User.role` (`UserRoles` enum): `user` for every tenant account, `superadmin` for SaaS-provider staff. Gates routers via `checkPermissionByRole` (superadmin passes every gate) and unlocks `/api/v1/admin`.
  - Company role (`Role` / `UserRole`): `company_owner` > `company_admin` > `company_member`, hierarchy in `utils/companyRoleHierarchy.js`. Company permissions come **only** from company roles — `checkCompanyPermission` and the team controller give superadmins no bypass.
  - Superadmins have `company_id = null` and no company roles. Billing, team and files routers are mounted behind `checkCompanyMembership()` (403 `COMPANY_MEMBERSHIP_REQUIRED`). Code reading `req.user.company_id` must never run for a user without a company; never query `where: { company_id: null }` (it matches every superadmin).
- Passport local strategy; sessions stored in PostgreSQL (Prisma session store), cookie `app.sid` (`SESSION_COOKIE_NAME`), 24h, `secure` + `SameSite=None` outside `DEPLOY_ENVIRONMENT=localhost`.
- Session rows carry `user_id` so sessions are revocable per user (`sessionModel.js`). Password reset and password update revoke sessions inside the same `$transaction` as the credential write (`deleteUserSessionsInTx(tx, userId, keepSessionId?)` and `deleteUserPasswordResetTokensInTx(tx, userId)`); the standalone `deleteUserSessions` throws on failure - never swallow a revocation error.
- Shared deletion side effects (session revoke, company/subscription cleanup) live in `server/utils/userDeletionCleanup.js`, used by both self- and admin-delete.

## Database (Prisma 7)

- Schema: `prisma/schema.prisma`. Models PascalCase, columns snake_case. Generated client outputs to `server/config/generated/` (gitignored + eslint-ignored) — run `npx prisma generate` after schema changes; never edit or commit generated files.
- Runtime client uses the `pg` driver adapter (`server/config/prismaClient.js` → `PRISMA_POSTGRES_CONNECTION_STRING`); migrations use the direct URL (`prisma.config.ts` → `PRISMA_POSTGRES_DIRECT_URL`).
- Schema changes require: migration (`npx prisma migrate dev --name <change>`), `prisma/seed.js` update if models change, `.env.example`/README if new vars.
- `User.email` and `TeamInvites.email` are `citext` (extension created by `20261110100000_indexes_fks_citext_emails`): uniqueness and `where: { email }` lookups are case-insensitive in the database; validators still lower-case. `Session.user_id` and `TeamInvites.invited_by` are foreign keys to `User` with `onDelete: Cascade` - sessions and issued invites die with their user. Never put `@unique` next to `@id`.
- The seed refuses to run unless `DEPLOY_ENVIRONMENT=localhost` or `ALLOW_SEED=1` (`prisma/seedGuard.js`). Prisma 7 `migrate reset` does not seed - run `npx prisma db seed` afterwards.
- Seed creates 1 company (`Acme Corp`, 7-day trial subscription) + 4 users, password `Password123!`: `owner@acme.test` (platform `user`, `company_owner`), `admin@acme.test` (platform `user`, `company_admin`), `user@acme.test` (platform `user`, `company_member`) and `superadmin@platform.test` (platform `superadmin`, no company, no company role). A `CHECK` constraint on `User` (`20261021160000_detach_superadmins`) enforces `role <> 'superadmin' OR company_id IS NULL`.
- Onboarding: `POST /auth/register` (`username`, `password`, optional `companyName` — kept optional for older clients) creates the company, its trial and the user in one nested write; the registrant is the company's first user and gets `company_owner`. Everyone else joins through team invites.
- Historical quirk: the login/register request field for email is named `username` (validators, controllers, and OpenAPI schema all use it). Keep it consistent; do not rename casually.

## Logging

- Use `logInfo` / `logWarn` / `logError` from `config/loggerFunctions.js` (pino + Telegram). Telegram sends time out after 5 s and identical alerts (message + error name/message) are sent at most once per minute per process (`integrations/telegram/sendLogsToTelegram.js`); pino still logs every occurrence. No `console.log` in server code (only `app.js` startup lines with `eslint-disable`).
- Explanatory "why" comments use the `//*` prefix — follow it for rationale comments.

## Testing

- Jest, ESM mode (`NODE_OPTIONS='--experimental-vm-modules' jest`). Specs in `backend/tests/*.spec.js`, named `<unit>.spec.js`.
- Always `import { jest } from '@jest/globals'`. Mock modules with `jest.unstable_mockModule(...)` + top-level `await import(...)` (see `userDeletionCleanup.spec.js`).
- Unit tests are pure — mock the models/integrations; no database or network in tests.
- Add a spec when introducing non-trivial logic (middleware, utils, controllers with branching).

## Docker & deployment

- Prod image: `Dockerfile` (node:26.12-alpine, `tini` as PID 1, non-root, `HEALTHCHECK` against `GET /health`; `start.sh` runs `prisma migrate deploy` then `exec node --import tsx ./server/app.js` - keep its flags in sync with the `start` script). `prisma generate` runs at build time without a database: `prisma.config.ts` falls back to a placeholder URL when `PRISMA_POSTGRES_DIRECT_URL` is unset.
- Local: `docker compose up -d --wait database` (Postgres only, with a `pg_isready` healthcheck; there is no server service, dev Dockerfile or `start:docker` script - the API runs on the host) → `npx prisma migrate deploy` → `npm run start:local`.
- CI (`.github/workflows/docker-build-push.yaml`): a `test` job (backend `npm test` + `npx eslint .`, frontend `npx eslint .` + `npm run build`) gates both image jobs; images are pushed on `latest` / `next` branch pushes, tagged with the branch, branch-date and short commit SHA. `DEPLOY_ENVIRONMENT` (`localhost` | else) toggles rate limiters, cookie strictness and pretty-printed logs.
